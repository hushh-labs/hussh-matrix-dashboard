## Scope and architecture

- `src/server/instagram/client.ts`, `capabilities.ts`: server-only Instagram Login reader on `graph.instagram.com/v26.0`. Identity must resolve to configured string ID `17841436775785807` before a write. Account and media capabilities listed below were checked against official docs and read-only live responses for this company account.
- `src/server/instagram/credentials.ts`: reads the latest JSON Secret Manager version if configured; otherwise uses a process-only local bootstrap token. A Secret Manager version takes precedence so an old environment token cannot replace a refreshed token.
- `src/server/instagram/sync.ts`, `store.ts`: once-per-UTC-day worker guard, BigQuery lease, run record, account metadata, and deterministic upsert. A failed refresh leaves a prior observation untouched.
- `sql/instagram_analytics.sql`: additive BigQuery dataset/tables for account metrics, media, media metrics, sync runs, and lock. It is **never run at startup**. IDs are strings. The production migration was applied after isolated UAT validation. Metric/media partitions expire after 730 days and run partitions after 180 days; the account row holds only the latest current counts. Review these retention limits with the data owner as usage grows.
- `server.ts`: private stored-data endpoint `GET /api/analytics/instagram` and operator-only, same-origin `POST /api/instagram/sync`. Both require a signed-in session even if aggregate dashboard public mode is enabled. The Instagram response bypasses the shared analytics cache because `canSync` differs by user.
- `src/Dashboard.tsx`, `src/components/InstagramPanel.tsx`: existing navigation and surfaces, last successful sync, exact requested UTC bounds, stale/error states, additional account totals/current counts, a recent media table with sorting/pagination, and an owned-site UTM link builder. No trend chart is drawn because no genuine time series is stored.
- `scripts/ingest-instagram.ts`: local/Cloud Run Job entry point. `scripts/ingest-hushh-ai-with-instagram.mjs` is the command now used by the **existing** Hushh AI Search Console Job and its Scheduler override. It preserves that job's exit status and calls the Instagram worker once per UTC day through a DB guard. No new Scheduler job was added.

## Metric contract

`reach` is one `total_value` for the exact `since` and `until` Unix seconds sent to Meta, with `period=day` and `metric_type=total_value`. The worker requests the seven completed UTC dates preceding the current UTC date. The provider response observed during setup gave no reporting boundaries, so these remain null. Meta may use its own reporting timezone; do not infer provider day boundaries from the UTC request. Never add these rolling totals together or represent them as daily points. `4869` appears only in an explicitly historical test fixture.

Account `views`, `total_interactions`, and `accounts_engaged` use the same requested seven-day window and `total_value` response shape. `followers_count` and `media_count` are current count snapshots in the account row; they are not growth. The worker reads at most five recent media objects per day, keeping ID, media type, permalink, publish timestamp, and currently exposed like/comment counts. It reads native `reach`, `saved`, `shares`, and `views` media insights as `values[0].value` with `period=lifetime`. Their stored `metric_type=lifetime_snapshot`, `fetched_at` marks observation time, and deterministic keys reconcile later changes. Video is labelled Video because the IG Login response did not verify a Reel-specific type. Media table reads are limited to 100 records published within 90 days. Missing count fields stay null; hidden counts are not zero.

Value `0` is a valid available value. Missing values are `not_yet_available`; an optional API error is recorded per metric as `not_supported`, `permission_missing`, or `sync_failed` without overwriting a prior valid value. A reach failure is still a failed sync. A token error stops remaining optional requests. Neither rolling account reach totals nor media reach values are added together. Meta's own reporting timezone may differ from UTC; the API did not return provider boundaries in these observed shapes. No comments, DMs, follower lists, viewer identities, scraping, publishing, or advertising objects are collected. [Account insights](https://developers.facebook.com/documentation/instagram-platform/api-reference/instagram-user/insights), [media insights](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media/insights), and [media fields](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media) define these shapes; actual availability remains account and media dependent.

## Private credential setup

**Local:** set `INSTAGRAM_ANALYTICS_ENABLED=true`, `INSTAGRAM_USER_ID`, and `INSTAGRAM_GRAPH_API_VERSION=v26.0` in ignored `.env.local`. Enter the access token only in the current PowerShell process as `$env:INSTAGRAM_ACCESS_TOKEN` using a private terminal; do not paste it into chat, command history, a screenshot, or this repository. The local variable is a bootstrap read token and has no unattended refresh. `.env.local` is inside a OneDrive path on this workstation, so do **not** save the token there. `npm run ingest:instagram` uses that process environment.

**Hosted:** in Google Cloud Console → project `hushh-ai-prod` → Security → Secret Manager, create an existing-infrastructure secret named `metrics-instagram-credential`. Add a version whose **secret value** is JSON (shown here with placeholders only):

```json
{"accessToken":"<ENTER PRIVATELY>","tokenType":"unknown"}
```

Set `tokenType` to `long_lived` and add `issuedAt` and `expiresAt` as verified ISO UTC timestamps **only after** checking the generated token's actual type and expiration. Never derive either from the opaque string or the old seven-day test. If metadata remains unknown, reads can work but automatic refresh is disabled. The worker reads `projects/hushh-ai-prod/secrets/metrics-instagram-credential/versions/latest` through the Secret Manager API and writes a new version when a verified long-lived token is within 14 days of expiry and at least 24 hours old. It does not invent an OAuth refresh token. An expired token stops Meta reads and shows reconnect required. Reconnect privately by adding a new verified secret version, then run the worker. A refresh response is saved before the worker uses the new credential; an old bootstrap env value is ignored whenever `INSTAGRAM_CREDENTIAL_SECRET` is set.

The existing production deployment workflow sets **non-credential** `INSTAGRAM_ANALYTICS_ENABLED=true`, `INSTAGRAM_USER_ID=17841436775785807`, `INSTAGRAM_CREDENTIAL_SECRET=projects/hushh-ai-prod/secrets/metrics-instagram-credential`, and `INSTAGRAM_ANALYTICS_ADMIN_EMAILS=i-neelesh@hushh.ai` on the server only. The API version defaults to the observed-working `v26.0`; the BigQuery project/dataset default to `hushh-ai-prod/instagram_analytics`. The release gate checks exact values and rejects a plaintext `INSTAGRAM_ACCESS_TOKEN`. This reuses the existing secret rather than creating several new Secret Manager versions for non-secret settings; the account ID, resource name, feature flag, and operator email are visible to users with Cloud Run configuration access. Never put a raw token in `--set-env-vars`, a `VITE_` variable, or HTTP tracing. The existing Search Console Job needs the same non-credential settings, but no operator email. On 2026-09-29, `roles/secretmanager.secretAccessor` was granted on this one secret to the dashboard and Job runtime service accounts; `roles/secretmanager.secretVersionAdder` was granted only to the Job runtime service account. Manual dashboard sync deliberately reads without refreshing. The dashboard runtime service account was given WRITER access only on this new BigQuery dataset; the existing Job account already had project BigQuery writer/job rights. [Google's Secret Manager roles](https://docs.cloud.google.com/secret-manager/docs/access-control) document those grants.

The earlier setup screenshot exposed an Instagram app secret. The owner confirmed it was reset on 2026-09-29, but this was not independently verified. This worker does not use that secret and does not change Meta app settings or existing permissions.

## Scheduling and resource limits

The project has three enabled Cloud Scheduler jobs in `hushh-ai-prod/us-central1`, for the three Search Console ingestions. On 2026-09-29, the **existing** `hushh-ai-search-console-ingest` Cloud Run Job image/command and its Scheduler container override were updated from `scripts/ingest-hushhtech-search-console.mjs` to `scripts/ingest-hushh-ai-with-instagram.mjs`, retaining `--days 16`, the existing Search Console secret binding, runtime service account, target URI, and `30 */6 * * *` UTC schedule. The wrapper runs Search Console first and checks Instagram's once-daily guard. Its successful exit status is the Search Console status; Instagram failures are logged separately. A protected manual `gcloud scheduler jobs run` created execution `hushh-ai-search-console-ingest-bkvqz`, which completed successfully, and its Instagram worker logged `already_synced_today`. This verifies Scheduler wiring and the guard under manual invocation. **No naturally timed Scheduler execution was observed during the release**, so automatic timing remains pending observation.

The worker makes at most 27 Meta GETs per daily attempt: identity, reach, profile, three other account insights, one media page, and four insights each for five media. Each request has a 10-second timeout and at most three bounded attempts for transient failures; the worst case request count is 81, though rate-limit or credential errors stop optional reads. Optional work stops starting new requests after 240 seconds so manual sync has headroom under the existing dashboard service's observed 300-second request timeout; the existing Job's observed task timeout is 1,800 seconds. Scheduled attempts stop after one attempt per UTC day. Manual sync requires an allowlisted operator email, same-origin request, 15-minute cooldown, and the same distributed BigQuery lease. BigQuery jobs have a 100 MB per-query billed-bytes cap. Dashboard account reads look back at most 30 days, and media reads at most 90 days/100 rows. These limits bound use but do not guarantee a zero bill: BigQuery query/storage free usage, Cloud Run Job runtime, network egress, and Secret Manager version counts are shared billing-account resources. Google currently documents [three free Scheduler jobs per billing account](https://cloud.google.com/scheduler/pricing), [BigQuery usage-based billing](https://cloud.google.com/bigquery/pricing), and [Cloud Run Job runtime billing](https://cloud.google.com/run/pricing). Check this billing account before approving the job change. No new vendor, hosting plan, Scheduler job, or paid connector is required by the code.
