- `src/server/instagram/sync.ts`, `store.ts`: once-per-UTC-day worker guard, BigQuery lease, run record, account metadata, and deterministic upsert. A failed refresh leaves a prior observation untouched.
- `sql/instagram_analytics.sql`: additive BigQuery dataset/tables for account metrics, media, media metrics, sync runs, and lock. It is **never run at startup**. IDs are strings. The content expansion adds media product type and inventory coverage fields through additive `ALTER TABLE` statements. Metric/media partitions expire after 730 days and run partitions after 180 days; the account row holds only the latest current counts. Review these retention limits with the data owner as usage grows.
- `server.ts`: private stored-data endpoint `GET /api/analytics/instagram` and operator-only, same-origin `POST /api/instagram/sync`. Both require a signed-in session even if aggregate dashboard public mode is enabled. The Instagram response bypasses the shared analytics cache because `canSync` differs by user.
- `src/Dashboard.tsx`, `src/components/InstagramPanel.tsx`, `src/lib/instagram-content.ts`: existing navigation and surfaces, last successful sync, exact requested UTC bounds, stale/error states, account totals/current counts, a content inventory with Reel/Feed counts, date/type filters, per-item metric coverage, sorting/pagination, and an owned-site UTM link builder. No trend chart is drawn because no genuine time series is stored.
- `scripts/ingest-instagram.ts`: local/Cloud Run Job entry point. `scripts/ingest-hushh-ai-with-instagram.mjs` is the command now used by the **existing** Hushh AI Search Console Job and its Scheduler override. It preserves that job's exit status and calls the Instagram worker once per UTC day through a DB guard. No new Scheduler job was added.

## Metric contract

`reach` is one `total_value` for the exact `since` and `until` Unix seconds sent to Meta, with `period=day` and `metric_type=total_value`. The worker requests three independent windows ending at the most recent completed UTC midnight: 7, 30, and 90 days. The first 7-day read remains required; longer windows are optional and can fail independently. The provider response observed during setup gave no reporting boundaries, so these remain null. Meta may use its own reporting timezone; do not infer provider day boundaries from the UTC request. Never add these rolling totals together or represent them as daily points. `4869` appears only in an explicitly historical test fixture.

Account `views`, `total_interactions`, and `accounts_engaged` use independently requested 7-, 30-, and 90-day windows and the same `total_value` response shape when available. The dashboard selects exact stored windows; it never mixes optional metrics from a different interval. Its post publication-date filter is separate from the account reporting-window selector. `followers_count` and `media_count` are current count snapshots in the account row; they are not growth. The worker scans at most 75 media objects across three pages of 25, retaining current ID, `media_type`, `media_product_type`, safe permalink, publish timestamp, and exposed like/comment counts for items in the past 365 days. It records whether provider pagination reached its end; a capped scan is visibly partial. A Reel is identified only by `media_product_type=REELS`, not inferred from `VIDEO`. One verified combined media insights request obtains native `reach`, `saved`, `shares`, and `views` for each scanned item. These are `values[0].value` with `period=lifetime`; their stored `metric_type=lifetime_snapshot`, `fetched_at` marks observation time, and deterministic keys reconcile later changes. Failed optional reads preserve prior valid values. Inventory metadata and available media insights use bounded BigQuery batch MERGEs, and dashboard media reads are limited to the latest scanned 75 records within 365 days. Missing count fields stay null; hidden counts are not zero. Summed per-item likes or views are labelled as sums of latest lifetime snapshots, never unique account reach.

## Private credential setup

**Local:** set `INSTAGRAM_ANALYTICS_ENABLED=true`, `INSTAGRAM_USER_ID`, and `INSTAGRAM_GRAPH_API_VERSION=v26.0` in ignored `.env.local`. Enter the access token only in the current PowerShell process as `$env:INSTAGRAM_ACCESS_TOKEN` using a private terminal; do not paste it into chat, command history, a screenshot, or this repository. The local variable is a bootstrap read token and has no unattended refresh. `.env.local` is inside a OneDrive path on this workstation, so do **not** save the token there. `npm run ingest:instagram` uses that process environment.

**Hosted:** in Google Cloud Console → project `hushh-ai-prod` → Security → Secret Manager, create an existing-infrastructure secret named `metrics-instagram-credential`. Add a version whose **secret value** is JSON (shown here with placeholders only):

```json
{"accessToken":"<ENTER PRIVATELY>","tokenType":"unknown"}
```

Set `tokenType` to `long_lived` and add `issuedAt` and `expiresAt` as verified ISO UTC timestamps **only after** checking the generated token's actual type and expiration. Never derive either from the opaque string or the old seven-day test. If metadata remains unknown, reads can work but automatic refresh is disabled. The worker reads `projects/hushh-ai-prod/secrets/metrics-instagram-credential/versions/latest` through the Secret Manager API and writes a new version when a verified long-lived token is within 14 days of expiry and at least 24 hours old. It does not invent an OAuth refresh token. An expired token stops Meta reads and shows reconnect required. Reconnect privately by adding a new verified secret version, then run the worker. A refresh response is saved before the worker uses the new credential; an old bootstrap env value is ignored whenever `INSTAGRAM_CREDENTIAL_SECRET` is set.

## Scheduling and resource limits

The project has three enabled Cloud Scheduler jobs in `hushh-ai-prod/us-central1`, for the three Search Console ingestions. On 2026-09-29, the **existing** `hushh-ai-search-console-ingest` Cloud Run Job image/command and its Scheduler container override were updated from `scripts/ingest-hushhtech-search-console.mjs` to `scripts/ingest-hushh-ai-with-instagram.mjs`, retaining `--days 16`, the existing Search Console secret binding, runtime service account, target URI, and `30 */6 * * *` UTC schedule. The wrapper runs Search Console first and checks Instagram's once-daily guard. Its successful exit status is the Search Console status; Instagram failures are logged separately. A protected manual `gcloud scheduler jobs run` created execution `hushh-ai-search-console-ingest-bkvqz`, which completed successfully, and its Instagram worker logged `already_synced_today`. The naturally timed 18:30 UTC Scheduler attempt then created execution `hushh-ai-search-console-ingest-tfs7q`, completed successfully, and again logged `already_synced_today`. This verifies timer dispatch and the daily guard. A naturally timed execution performing the next day's Instagram ingestion remains to be observed.

The worker makes at most 92 Meta GETs per daily attempt when the account has at least 75 media items: identity, three reach windows, profile, nine other account insight/window pairs, three media pages, and one combined insight request for each media item. Each request has a 10-second timeout and at most three bounded attempts for transient failures; the theoretical retry ceiling is 276 requests, though rate-limit or credential errors stop optional reads. Optional work stops starting new requests after 240 seconds so manual sync has headroom under the existing dashboard service's observed 300-second request timeout; the existing Job's observed task timeout is 1,800 seconds. Scheduled attempts stop after one attempt per UTC day. Manual sync requires an allowlisted operator email, same-origin request, 15-minute cooldown, and the same distributed BigQuery lease. BigQuery jobs have a 100 MB per-query billed-bytes cap. Dashboard account reads look back at most 30 days by observation end date and return at most twelve window/metric rows; media reads remain at most 365 days/75 rows. These limits bound use but do not guarantee a zero bill: BigQuery query/storage free usage, Cloud Run Job runtime, network egress, and Secret Manager version counts are shared billing-account resources. Google currently documents [three free Scheduler jobs per billing account](https://cloud.google.com/scheduler/pricing), [BigQuery usage-based billing](https://cloud.google.com/bigquery/pricing), and [Cloud Run Job runtime billing](https://cloud.google.com/run/pricing). No new vendor, hosting plan, Scheduler job, or paid connector is required by the code.
