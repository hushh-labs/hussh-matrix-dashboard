# One agent-detail manual collection: integration boundary

This is a design checkpoint, not an enabled collector. The current dashboard Refresh sends `X-Metrics-Passive-Read` and returns an authorized retained report or an unavailable response. It does not run a new One export query. The `one.adoption` report contains only active accounts and confirmed outcomes and must not be substituted for the 67 feature records or the complete legacy dashboard.

## Existing source and result boundaries

The extracted `oneFeatureUsageQuery` preserves the existing feature query and adds distinct Receipts workspace and single-contact result mappings; it does not construct or authorize its table, surface filter, or date range and it does not execute a query. A producer must obtain those fragments from a trusted environment-specific configuration, apply the verified UAT surface and source calendar, and never accept SQL fragments from a request. The existing Location panel uses a separate Location behavior query for its devices, signals and outcome counts; combining only the feature query would silently change that metric. Missing sparse rows or zero-spined Location rows cannot establish observed zero. Feature result rows also have event breakdowns, and the full One payload includes capability, daily, Location and other sections not represented by the proposed 67-row subset.

`DailyOneRefresh.read` verifies run/activation lineage, report binding and the applicable cohort before returning a retained result. Its internal scope provenance contains the manifest binding and the selected report binding; neither is a GA4 information watermark. Warehouse job completion timestamps and snapshot computation time do not prove GA4 ingestion or source finalization. The disconnected subset adapter must receive trusted policy-bound digests and an independently verified source calendar. Its source check time and watermark remain unknown when that evidence is unavailable.

## Required implementation before a manual compute path

1. Define a versioned, bounded result variant for the actual detail subset and any additional fields the consuming UI needs. Extend the existing reporting registry, request/result validation, storage envelopes and reader together. Keep `one.adoption` separate. Require explicit source and environment bindings; reject partial, malformed, mixed-lane or wrong-period results, and retain unknown dimensions as unknown.
2. Admit an authorized manual request through the existing transactionally coalesced report job and capacity policy. Give each logical environment, source generation, period, definition and scope a stable key. Normal page reads remain passive. Status/read endpoints must not submit work, and repeated clicks must join the same durable active job rather than enqueue duplicate source jobs.
3. Introduce a separately approved BigQuery source and worker identity/runtime. The current reporting worker requires `METRICS_BIGQUERY_ENABLED=false`, while the legacy guarded executor has its own shared daily ledger and fixed ceilings. Do not loosen the worker guard, create an independent uncapped bypass, or reuse the historical first-fill 1 TiB limit as a recurring allowance. The approved policy must cover all BQ-producing paths that share the budget, enforce native per-job and UTC-day byte/job limits, and retain charged reservations after uncertainty.
4. Before each new paid job, run a fresh native precise/upper-bound estimate plus the conservative referenced-table floor, check the remaining shared durable budget in a transaction, reserve the exact bound, then fence a stable native job ID before submission. Reconcile an uncertain submission by that same ID and verified native project/location/query/config; missing or mismatched evidence must hold the job, never start a replacement. Ordinary rendering and cache misses cannot trigger estimates or paid work.
5. Publish an immutable, size-bounded snapshot only after every required source result and authority/cohort recheck succeeds. Bind the definition, environment, exact period, report and source scopes, job receipts, producer source and measured query clock. Preserve the previous publication on failure. Explicitly report unknown/intraday source coverage and avoid calling job completion a data watermark. An observation absent from a best-effort feed is not proof of no user action.
6. Prove cross-instance coalescing, native budget contention, lost acknowledgements, authorization changes, date rollover, malformed/partial result rejection, lane isolation and passive-read no-query behavior with local fakes and normal CI. Then obtain native free estimates and a measured operating policy before any bounded collection or production activation. No native estimate, monetary cost or complete capture guarantee is established by this design.

The Receipts workspace and single-contact result events change the detailed catalog and query digests. Earlier 64- or 65-row publications do not satisfy the current exact manifest; they require independent requalification and must not be interpreted as containing historical Receipts workspace views.
