# Metrics loading and freshness

Date filters select an exact period. The page only renders a response belonging to that period; an uncached period has a local skeleton while its controls and navigation remain usable. Returning to a previously viewed period reuses the browser's session-only cache. Custom dates are applied together with **Apply dates**, avoiding a warehouse query for every edit.

The dashboard requests only the selected section (`view=one`, `growth`, `apps`, `overview`, or `platforms`). Growth and Hushh Connect share One's selected range. Apple reporting in Hushh Connect also receives that range. Overview retains the independent web and hushh.ai ranges and skips unused app, billing, and Apple reports. Platforms shares the same source snapshot as Overview. All 16 common web/hushh.ai date combinations are prepared in the background. The unscoped API retains its complete contract for existing consumers. The over-time comparison uses its own endpoint. Counts and KPI formulas are unchanged: identities remain distinct within their original property and period, and missing sources remain unavailable.

Authenticated aggregate responses use bounded in-process snapshots. Responses stay `Cache-Control: no-store`; the snapshot is never stored by a public CDN. Exact dates, query scope, and environment remain part of the key. Concurrent requests for the same snapshot share one computation. Snapshots start refreshing after 60 seconds and expire after 10 minutes. An expired snapshot requires a completed source read before being shown again. Recently used snapshots refresh in the background; common 7/14/30/90-day ranges are prepared at startup and every five minutes, including UTC date rollover. Warm-up is sequential and background refresh has two workers. BigQuery clients are reused, and matching SQL work shares a bounded 30-second cache.

**Refresh** immediately returns an existing matching snapshot and starts a source read behind it. The UI says **Refreshing in the background**, then polls every 1.5 seconds until the snapshot completes. **Updated** is the snapshot's completion timestamp, not the time a cached response was served. A failed refresh preserves its dated last success and shows an error; it does not replace it with estimated values. Provider export dates and ingestion delays remain visible separately. GA4's export delay does not disappear when Refresh is clicked.

The browser caches up to 48 resources for at most ten minutes, checks the current visible section every 30 seconds, and prefetches common periods after the current one renders. Cache data is cleared on logout and authorization failure, including protection against an old in-flight response repopulating the next session. Instagram's operator permission remains calculated per authenticated request and is excluded from the shared response cache.

JavaScript for secondary panels loads on demand. The login check and dashboard use an accessible light skeleton. API responses and static files use gzip when supported. Production uses one warm Cloud Run instance and CPU outside requests so the timers can run between visits. Cloud Run session affinity keeps sequential browser requests on the same instance when it has capacity, which improves reuse of its prepared snapshots. Affinity is best effort: an instance replacement or overload can still move a browser to a cold instance. Authentication remains separate and stateless.

The 1–2 second acceptance target applies to prepared/common ranges, revisits, and the response to Refresh. A new custom range or a newly scaled instance can still require a longer warehouse/provider query; the page shows the pending range and a skeleton for that work. No old-period numbers are relabeled as the new range.

Validation: `npm test`, `npm run lint`, `npm run build`, existing metric/reconciliation release probes, and `scripts/check-metrics-performance.mjs` with the signed release-fetch adapter. The adapter holds only the Cloud Run routing cookie in memory alongside the QA session and sends both only to the exact verified origin. `npm run test:deploy:release-fetch` verifies that boundary. The performance probe checks all common One/Growth/Connect ranges, exact dates, private-response headers, aggregate privacy, a completed background Refresh, and the 2,000 ms warm-response budget. Browser QA separately verifies skeletons, rapid changes, cached revisits, custom Apply dates, and desktop/mobile layouts.
