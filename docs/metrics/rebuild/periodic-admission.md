# Periodic collector admission

This is a default-off admission capability for the replacement collector. It does not create a scheduler, enable collection, seed a policy, change the live dashboard, or approve an operating cost. The existing cost hold and paused delivery remain in place until the source authorities, reporting definitions, reconciliation and measured operating policy are accepted under issue #184.

An approved `periodic` policy may name fixed report entries and up to three UTC trigger windows. Each entry declares a report definition, source reporting timezone, period length and end-day lag. The dispatcher supplies only an entry ID; it cannot choose a date, source, URL or query. Source-calendar dates are calculated for the selected window and remain subject to the existing report control and source validation. An end-day lag of zero does not imply that a source day is complete.

The collector atomically records a UTC-day admission counter, a window/entry receipt, the cycle head and the existing report job/dispatch intent. Repeated triggers reuse the receipt and return the durable job or publication state; they do not create another job. A later window cannot start while a job referenced by the previous window is unresolved. The active cycle's jobs are protected from maintenance pruning. A tighter observed daily limit is retained for the rest of that UTC day. Missing or malformed control, uncertain source work, exhausted capacity, and conflicting policy changes fail closed. Existing report reads remain passive.

`maxDailyJobs` limits **new jobs created by this periodic path**, across its windows and collector instances. It is not a currency limit, a BigQuery byte limit, or a cap on custom jobs, manually scheduled jobs when periodic mode is disabled, other services, or legacy collectors. The existing journaled adapters independently reserve their approved source-specific daily read/request budgets across collector job lanes before provider I/O; those units are not monetary guarantees. The replacement worker currently requires BigQuery disabled and has no legacy One BigQuery refresh adapter. A future BigQuery integration must have its own reviewed, native per-query byte limits, stable job reconciliation and durable cross-run daily reservation before use.

Disabling the periodic policy prevents new periodic admission; already accepted work remains governed by the collector's existing source journals and recovery rules. To hold all collection, use the existing collection/compute controls and paused delivery, without refunding uncertain reservations. No automatic cleanup of periodic receipts or counters is introduced; a retention policy must protect unresolved work and be reviewed before production operation.

Before any activation, establish identity and source access, complete the Next.js/collector boundary, measure source-specific marginal cost and latency for the intended workload, reconcile outputs and watermarks, and have the operating policy reviewed as required by #184. In particular, the one-time restoration's bytes and billed total are not a recurring-cost estimate. The availability and definitions of 90-day One, Android, first-open, retention and Search remain separate source-coverage questions.
