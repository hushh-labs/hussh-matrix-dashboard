# One app referral rankings

`/referral-analytics` shows only Individual and Circles standings. Individual rows contain the published rank, public member handle and score, labelled Points. Pages contain at most 20 entries. Previous/Next pin the same source snapshot so a newly published ranking cannot move members between pages. Refresh starts at the latest snapshot.

The source is the One app's published PostgreSQL leaderboard, not GA4 page views or a sum of referral events. The score comes directly from `one_referral_leaderboard_snapshot_entries.cumulative_points`, matching the app's `points` API field. The app currently calls this score Coins; the dashboard uses the requested Points label without recalculating it. Do not substitute `SUM(points)` from the score ledger: that is a different measure.

Member labels follow the current One app contract: a chosen `one_referral_display_handles` alias takes priority; otherwise use a profile name permitted to the signed-in viewer through Connect. The dashboard's verified session email is resolved to its matching enabled, verified Firebase account. No client-supplied viewer ID is accepted. An unlinked or unverified viewer receives aliases and anonymous placeholders only.

`referral_rankings_for_viewer(integer,uuid,text)` reads the same active-profile and vault/relationship eligibility as One's directory. Profile candidates must have an active vault or an active connection, pending connection request or active trusted edge with the viewer. The viewer's own name uses their Firebase profile. Firebase batch lookups verify candidates still exist and are enabled before using SQL names, with Firebase/provider display names filling otherwise unnamed legacy profiles. Raw UIDs, UUID labels, email addresses and phone numbers never substitute for names. Unavailable or ineligible names remain `Anonymous referrer`.

This endpoint requires a dashboard session even in public aggregate mode. Viewer-permitted responses bypass the shared aggregate cache. Candidate UIDs and cached profile fields remain server-side; each public row still contains only rank, member label and points. The One app's `one_referral_identity_service` and Connect directory are the authority for eligibility, not registration alone. Firebase lookups use the same configured auth project and runtime identity as the existing registered-account report ([API contract](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/accounts/lookup)).

The app's Circles leaderboard currently returns `status=preview`, `competition_active=false` and no teams. The dashboard preserves “No circle standings yet.” rather than creating standings from private circle records. Pagination remains disabled until that product contract publishes standings.

## Source selection and freshness

`GET /api/analytics/one/referrals` accepts `board=individual|circles`, optional `environment=production|uat`, `afterRank` (default 0) and optional UUID `snapshotId`. A nonzero cursor requires an explicit environment and snapshot ID. Page size is fixed at 20; there is no date filter because the ranking is cumulative.

Without an explicit environment, choose Production if it has published entries, otherwise UAT if it has entries. Show environment buttons only when both have entries. A failed source remains unavailable; it is never treated as empty. No published snapshot is `waiting`; a removed pinned snapshot is `expired` and offers a restart. A published snapshot with no stored entries is genuinely empty. The timestamp displayed is the snapshot generation time, not query time.

A read-only check on 20 October 2026 found published entries in both environments: Production 329 stored entries (snapshot 18 October 21:41:50 UTC), UAT 105 (19 October 21:16:41 UTC). Production's snapshot header says 330; one stored entry is absent. Display existing published ranks and count actual stored entries for source selection; do not invent a missing member or renumber the leaderboard. The ranking SELECT was verified read-only across all 17 Production pages and 6 UAT pages, with no duplicate ranks between pages. At that earlier check optional aliases were absent. That does not mean registered profile names are missing: the current app resolves those through a separate viewer-permitted directory projection. Snapshot membership and scores can change as the app publishes newer snapshots.

## Runtime connection

1. Install [the ranking projections](../src/server/referral-rankings.sql) as the database owner in Production (`hushh-pda:us-central1:hushh-vault-db`, database `hushh_vault`) and UAT (`hushh-pda-uat:us-central1:hushh-uat-pg`, database `postgres`). They read existing snapshots and eligible directory profiles; they never publish snapshots or change referral records. Install the viewer-aware function before rolling out its server code; the base function remains compatible with older revisions.
2. Use the existing dedicated login with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT`, `default_transaction_read_only=on`, and `statement_timeout=15000`. Grant only database CONNECT, schema `metrics_dashboard` USAGE and EXECUTE on `metrics_dashboard.referral_rankings(integer,uuid)` and `metrics_dashboard.referral_rankings_for_viewer(integer,uuid,text)`. Do not grant underlying table access. Both SECURITY DEFINER functions have fixed search paths and no PUBLIC execution permission.
3. Reuse Secret Manager secrets `metrics-one-referrals-production` and `metrics-one-referrals-uat` in `hushh-ai-prod`. Each payload is a JSON object with `instance`, `database`, `user`, and `password`. Pass values securely; never commit or log them. This names update requires no credential rotation or new secrets.
4. Grant `metrics-dashboard-runtime@hushh-ai-prod.iam.gserviceaccount.com` Secret Accessor on only those secrets and Cloud SQL Client in both source projects.
5. Verify an authenticated dashboard session can page through the standings, while unsigned requests get 401. Verify two dashboard users never share a cached name response. Verify the database login can execute the projections but cannot select underlying account/referral rows. Source failures return a sanitized 503 rather than zeros; failed identity checks keep names anonymous without changing scores.

On 20 October 2026, the base ranking function and its EXECUTE grant to `metrics_referrals_reader` were installed in both sources and verified through the live signed-in dashboard, including 20-row pagination. Existing runtime connections work. The optional-alias-only projection explains why all unnamed aliases appeared anonymous even though the current One app separately resolves registered profile names. The viewer-aware update fixes that mismatch while keeping the visibility and current-account checks. Existing legacy aggregate grants should be retired only after older live revisions no longer use them.

Local checks: `npm run lint`, `npm test`, `npm run build`, `npx playwright test tests/ui/referrals.pw.ts`. UI tests use synthetic public handles; source checks are read-only and recorded separately. Production deployment remains subject to the existing Cloud Build/Cloud Run IAM permissions.
